The Problem

Everyone had an AI tool. None of them sounded like us. Then we decided to go global.

Last year AI became a daily habit across the content team, each writer on a personal subscription with no shared rules. The drafts were fast, did not sound like Financial Finesse, and nothing recorded which claims had been checked. I chose to solve control before speed: one place to write, with voice and compliance rules applied by default and a record of what was checked. Then the company set its sights on every market, and the same tool had to localize the library.

592 English source pieces × 25 target markets ≈ 14,800 localized outputs, and one in-country localizer per market to recruit and manage.
Financial advice changes by country: tax structures, retirement systems, and regulations are all different.
Tone, customs, and ways of life shape how money is discussed. A literal translation would be technically correct and wrong for the reader.
Getting it wrong in a financial context is not a typo. It is a liability.

The Workflow

Two people, one tool: the author and the localizer

Two jobs, one tool. The author sees, while drafting, which claims the model could not source. The localizer works a per-locale queue with source and localized text side by side, and nothing reaches a member until that person approves it.

01

The author picks a content type, a locale, and an audience, then writes a topic. Every request carries the voice pillars, the compliance rules, and the schema for that content type through the Anthropic API behind a Worker. The draft comes back as a quiz, an article, or a checklist.

02

Uncertainty is shown, not hidden. The model must cite a source it consulted or flag the claim. Flagged claims appear in an accuracy-check panel beside the editor, each with the figure to confirm and where to confirm it, and the author resolves them before saving.

03

The localizer gets a queue, not a firehose. Localize QA shows each locale's need-review, approved, and flagged counts, so the person decides where to spend the day. Inside a piece, source and localized text sit side by side with the verify pass's typed problems attached.

04

Status is the contract between people and automation. Draft, in review, approved, published. Nothing auto-publishes; the policy is in the code. A batch run may create and update variants in review. It may not touch an approved one unless a person asks (that rule has a history, below).

The Pipeline

Inside Atlas: what happens to every article

Every article, new or localized, moves through Atlas: a fit check decides whether the piece belongs in that market at all, then eight controlled steps run. The model's confidence is a routing signal, never a guarantee. What decides whether anything publishes is the fit check, a separate verify pass, deterministic checks for US-only terms and links, and the localizer.

Decisions and tradeoffs

Four calls I would make again

A per-locale wiki instead of open-web search

Not taken: letting the model research each market live on the web at draft time.

Why: financial facts have to be ours. A curated wiki is slower to build, one locale at a time, but every retirement system and tax authority the model cites is something a person vetted. Web search still runs in the research stage; it feeds the wiki, it does not bypass it.

Five model calls per article, not one

Not taken: the original one-pass pipeline, which cost about a fifth as much.

Why: one-pass output kept US framing and US-only links that no automated check could see. Splitting into gate, research, draft, independent verify, and save took an article to roughly 335k tokens. That cost is what forced the skip-approved default and targeted re-runs instead of full-corpus rewrites.

The score routes; it does not gate

Not taken: publishing anything above a confidence threshold.

Why: the confidence number is the model grading its own output. It is useful for deciding what a reviewer sees first and useless as a guarantee. The gate is a separate verify pass with typed failure reasons and a redo loop, deterministic checks, and a person. There is no threshold in the code, on purpose.

One Worker holds every secret

Not taken: calling the Anthropic API and Azure from the browser, which is faster to build and one less deploy.

Why: ordinary practice, but it shaped the product: with one write path, there is one place to enforce the status rules above. The cost is a second deploy target and a hand-written Azure client, since the SDK cannot run in Workers.

Building with AI

One feature, start to finish: the verify stage

AI sits in both halves of the work: Claude Code as the pair for the app and the workflow, the Anthropic API inside the product. One feature traced through, using only what the repo and its logs record.

01

The problem. Localized articles kept first-party links to US-only content (HSAs, 401(k)s) and US framing, and every automated check passed them. A reader in Ireland would follow a link to advice that does not apply. The fix could not add a person to every article; the queue was already 1,800 deep.

02

The options. Tighten the draft prompt and hope; add a deterministic link check; add a second model pass that reads the draft the way a native reader would. I rejected the first as unmeasurable and took both of the others, because they fail differently: the link check cannot miss a URL, and the verify pass sees framing a regex cannot.

03

Where AI did the work, and where I said no. The verify stage is a model call with a typed vocabulary of failures (us-comparison, us-institution, literal-idiom, us-currency-or-format, us-only-framing, terminology-violation, register-slip) and a pass-or-fail verdict that triggers a redo. The stage, its schema, and the fan-out workflow were written with Claude Code. What I did not accept: the model's own confidence score as a quality signal, since it is self-grading, so it routes and never gates; and fluent one-pass drafts that still carried US assumptions, which are exactly what the stage exists to fail.

04

How it was checked. Vitest covers the gate, the policy, the rewrite, and the index logic (221 tests, September 2026). The link check ran against real data first: 51 dangling call-to-action phrases across 27 locales and 8,120 variants. The fit check was measured the same way: of 75 UK articles it dropped, 13 had a UK analogue and were rewritten; 62 could not honestly exist there. Then the localizers reviewed the output, which is the check that counts.

05

What shipped, and its limits. The verify stage with its redo loop, plus a link check that wraps, aligns, or strips a link and rewrites the sentence it left dangling; the localizer sees each typed problem as a label to act on, not a number. US-only links stopped reaching review. Cost per article rose about five times, so approved work is skipped by default and re-runs are targeted. The localizers still catch what no pass does: a figure tied only to a secondary source, a slug left in English.

What broke and what changed

Five production failures, and the fix for each

The one that changed the product

A batch run erased a localizer's approved work

What happened

A 25-article es-MX batch reported "25 written, 0 errors." It had consumed variants a localizer had already reviewed and approved, and replaced them with fresh model output. Measured on three reviewed articles, none of the reviewed sentences survived: 26 of 26, 32 of 32, 32 of 32 were gone.

What people lost

Hours of a native speaker's judgment, silently. The run looked like a success in the log and in the library. The only signal was a localizer recognizing text she had already corrected.

What changed in the workflow

Approved became a state automation cannot cross. A run skips approved variants by default and reports them as skipped, so the count a person reads matches what the run was allowed to touch. Re-localizing an approved piece is an explicit, named request (includeApproved), made by a person, on purpose.

What validates it

The rule is code, not convention: it lives with the pipeline's policy logic, which carries its own tests, and it is enforced on the one write path every run uses. The decision is dated August 5, 2026, and it is mine.

5,455 published variants carried English titles and slugs on localized bodies

Found in the live data during an August audit, not by a user. Title and slug localization is now a checked output of the packager, and the review console shows source and localized titles side by side.

US-only links were invisible to every automated check

The verify stage and the link check above. The first full scan found 51 dangling call-to-action phrases across 27 locales and 8,120 variants.

Five different locale briefs for the first five articles of every batch

The 5-worker pool derived the per-locale brief in parallel before the cache was written: five model calls and five inconsistent briefs. The fix is a keyed single-flight lock with its own tests. A cached brief was later caught still using the wrong register, which led to brief versioning.

A pass failed silently and the job sat at "running" forever

The cultural pass threw a JSON parse error that was swallowed. Unparseable model output now fails the job with a retry, and a count check throws rather than saving a partial article.

Architecture

Four parts, one write path

A static TypeScript and Lit app on Vercel and a CLI localization workflow both talk to one Cloudflare Worker. The Worker holds the secrets, proxies the model calls, and fronts Azure Blob Storage, where every entry, variant, wiki page, and QA flag lives. One write path means one place to enforce the status rules.
